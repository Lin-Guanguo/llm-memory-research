## 1. Overview

**"Memory in the Age of AI Agents"** is a 47-author survey (lead: Yuyang Hu; main contact: guibinz@u.nus.edu) published to arXiv on 2025-12 as 2512.13564. It is the first large-consortium attempt to impose a coherent taxonomy on the explosion of "agent memory" work that followed MemGPT (2023), Reflexion (2023), Voyager (2023), Mem0 (2024), and the 2025 wave of production memory services (Letta, Graphiti/Zep, Hindsight, Mastra, MemOS, Supermemory, ChatGPT Memory, Claude Memory).

The paper's central diagnosis is **terminological fragmentation**: the existing literature mixes cognitive-science borrowings (episodic, semantic, procedural, declarative) with systems vocabulary (vector store, KV cache, LoRA adapter) and product vocabulary (short-term, long-term, working), with no shared axis to compare a "Mem0 graph memory" against a "MemoryLLM latent memory" against a "ROME parametric edit". The survey's response is to replace the old long-term/short-term dichotomy with a three-axis framework:

1. **Forms** — the *substrate* in which memory lives (tokens, weights, latents).
2. **Functions** — what memory is *for* (facts, experience, workspace).
3. **Dynamics** — how memory *changes* over time (formation, evolution, retrieval).

It also draws explicit conceptual borders against three sibling concepts:

| Concept | What it is | How it differs from agent memory |
|---|---|---|
| **LLM memory** | KV cache, long-context attention, streaming transformer variants | Architectural, single-context; does not persist across tasks |
| **RAG** | Static document retrieval for a single inference | Read-only, not self-evolving, no agent-authored content |
| **Context engineering** | Prompt/context packing and interface tuning | Allocation problem within one call; no persistent state |

**Why it matters for this repository.** Our `*.research.md` collection (Mem0, Letta, Graphiti, Hindsight, Mastra, MemOS, Supermemory, ChatGPT, Claude, OpenClaw) grew organism-by-organism; each report uses the vendor's own vocabulary. This survey gives us a single coordinate system to pin all of them onto. The most useful consequence is that we can now name structural differences that vendor docs obscure (e.g., Mem0 and Hindsight both call themselves "graph memory", but sit in different cells of the Forms axis once you distinguish planar from hierarchical token-level memory).

**Source:** [arXiv abstract](https://arxiv.org/abs/2512.13564) | [Paper list GitHub](https://github.com/Shichun-Liu/Agent-Memory-Paper-List) | [alphaXiv overview](https://www.alphaxiv.org/abs/2512.13564) | [emergentmind summary](https://www.emergentmind.com/papers/2512.13564)

## 2. The Taxonomy

The survey's organizing diagram is a 3×3 cube: Forms × Functions × Dynamics. Each axis has three top-level buckets, most of which are further sub-divided. The textual skeleton below reproduces the hierarchy reported by alphaXiv and the companion paper list.

### 2.1 Forms — where the memory physically lives

```
Forms
├── Token-level (explicit, discrete, externally inspectable)
│   ├── Flat (1D)        — no inter-unit topology
│   │                      Examples: MemGPT buffer, ExpeL, Reflexion trace
│   ├── Planar (2D)      — single-layer structured
│   │                      Examples: A-MEM, Memo^g (graph); MemTree, HAT (tree)
│   └── Hierarchical (3D) — multi-layer, inter-layer links
│                          Examples: GraphRAG, HippoRAG, Zep/Graphiti, AriGraph
├── Parametric (encoded in weights)
│   ├── Internal         — direct weight modification
│   │                      Pre-train/SFT: StreamingLLM, LMLM, TNL
│   │                      Post-train edit: ROME, MEMIT, AlphaEdit
│   └── External         — auxiliary parameter sets
│                          LoRA / adapters / proxy models: Retroformer, "Early Experience"
└── Latent (implicit hidden state)
    ├── Generate         — produce new latent representations (MemGen, SoftCoT, SoftCoT++)
    ├── Reuse            — leverage existing latent spaces (LM2, Titans)
    └── Transform        — modify latent structures (MemoryLLM M+, MemoRAG, Memory³)
```

**Definitions (distilled):**
- **Token-level memory** — explicit text/graph/tree/vector units that can be printed, diffed, and stored in a database. Fully interpretable, trivially editable, but must be retrieved through an explicit query mechanism. This is where almost every production system lives today.
- **Parametric memory** — knowledge fused into the weights of the model itself (full fine-tune, LoRA, or targeted edit via ROME-family methods). Offers free "retrieval" (knowledge is always active) and generalization, but is hard to edit, hard to audit, and risks catastrophic forgetting.
- **Latent memory** — information kept in continuous hidden activations / KV-style caches / learned embedding slots. Machine-native — not human-readable — but can carry sub-symbolic patterns that tokens cannot express economically.

### 2.2 Functions — what the memory is for

```
Functions
├── Factual memory           — declarative facts about user, environment, world
│                              Examples: MemoryBank, ChatHaruhi, Mem0, Graphiti, Hindsight (world/experience)
├── Experiential memory       — procedural / learned-from-doing
│   ├── Case-based           — concrete past trajectories (ExpeL, Memento, Reflexion)
│   ├── Strategy-based       — distilled procedures (Voyager skill library, AWM)
│   ├── Skill-based          — executable capabilities (DGM, ToolMem)
│   └── Hybrid               — combined (Agent-PLAN, Agent-Lumos)
└── Working memory            — task-local scratchpad
    ├── Single-turn          — within one interaction
    └── Multi-turn           — sustained across a session (HiAgent, ReSum, MemAgent)
```

**Definitions (distilled):**
- **Factual memory** is the "who/what/when/where" layer — declarative facts that persist independently of the task that generated them. It maps onto the episodic-to-semantic spectrum from cognitive neuroscience.
- **Experiential memory** is the "how" layer — procedural knowledge accumulated from attempts, reflections, and successful solutions. The sub-typing is important: storing a raw trajectory (case-based) is architecturally different from storing a distilled policy snippet (strategy-based) or a runnable tool/skill (skill-based).
- **Working memory** is the task-scoped scratchpad: summaries-of-summaries, planning state, current goal stack, observation abstractions. The survey explicitly separates this from long-term factual memory, matching production practice (e.g., Letta's core block vs. archival store, MemOS's WorkingMem vs. SemanticMem).

### 2.3 Dynamics — how memory changes over time

```
Dynamics
├── Formation    — how new memory enters the system
│   └── Semantic summarization | Knowledge distillation | Structured construction |
│       Latent representation | Parametric internalization
├── Evolution    — how existing memory changes
│   ├── Consolidation (local / cluster / global; merging, deduplication)
│   ├── Updating (modification, refresh, model editing)
│   └── Forgetting (selective pruning, decay, expiry)
└── Retrieval    — how memory is called back
    ├── Timing & intent       (when to retrieve? who decides?)
    ├── Query construction    (rewriting, decomposition, expansion)
    ├── Retrieval strategies  (lexical / semantic / graph / generative / hybrid)
    └── Post-retrieval        (filtering, compression, re-ranking)
```

The paper gives formal operators:

```
Formation:  M_{t+1}^{form} = F( M_t, φ_t )
Evolution:  M_{t+1}      = E( M_{t+1}^{form} )
Retrieval:  m_t^i        = R( M_t, o_t^i, Q )

Agent policy: a_t = π_i( o_t^i, m_t^i, Q )
```

where `φ_t` is the new evidence at step `t`, `Q` is the task spec, and `o_t^i` / `m_t^i` are agent `i`'s observation and retrieved memory signal. This formalism is the thinnest possible POMDP-style wrapper that lets you express every system in the survey as a choice of `F`, `E`, `R`.

### 2.4 The cube, in one picture

```
                 FORMS
              (token / param / latent)
                    ▲
                    │
                    │
                    │      DYNAMICS
                    │    (formation /
                    │     evolution /
                    │     retrieval)
                    │   ╱
                    │  ╱
                    │ ╱
                    └─────────────────▶ FUNCTIONS
                                        (factual / experiential / working)
```

Any system can be described as a subset of cells in this cube plus a choice of F/E/R operators. The survey's implicit claim is that **most production systems today are clustered on the (token-level, factual, retrieval-heavy) corner** and that the field's research frontier is the under-populated cells — parametric experiential memory, latent working memory, automated evolution, multi-agent shared memory.

## 3. Mechanism Families

The survey groups existing mechanisms along Dynamics rather than along vendors. The mapping below follows the categorization reported by emergentmind.

| Family | Representative mechanisms |
|---|---|
| **Formation** | Semantic summarization (rolling summary, chapter summary), knowledge distillation (LLM-as-teacher for extraction), schema structuring (entity/relation extraction → graph), latent encoding (Gist tokens, MemGen), parametric internalization (LoRA of recent logs) |
| **Evolution** | Local consolidation (dedupe within a cluster), cluster consolidation (entity merging), global consolidation (schema refactor), explicit updating (CRUD, contradict-and-replace, temporal versioning), model editing (ROME/MEMIT/AlphaEdit for parametric), forgetting policies (TTL, salience decay, importance-weighted eviction) |
| **Retrieval** | Timing (every-turn / LLM-decided / triggered), query construction (rewrite, decompose, expand), strategies (BM25, vector, graph traversal, generative/agentic RAG, hybrid RRF), post-processing (cross-encoder rerank, compression, filtering by recency/provenance) |
| **Memory-RL integration** | Heuristic policies → RL-assisted (reward-tuned retrieval or consolidation) → fully RL-driven memory management |
| **Test-time augmentation** | Rolling summaries, self-reflection loops, iterative refinement, token pruning (H2O), Gist token compression |

This is the view that lets one compare, say, **Graphiti's "bi-temporal edge invalidation"** against **Hindsight's "observation UPDATE/DELETE with temporal markers"**: both are instances of the *Evolution → updating* family, differing in whether the storage model is graph-native or fact-native.

## 4. Placement of Already-Researched Systems

| System | Form(s) | Function(s) | Formation | Evolution | Retrieval |

| **OpenClaw** ([openclaw.research.md](./openclaw.research.md)) | Token-level — Flat session scratchpad; relies on external memory via LLM wrappers (e.g., Hindsight, Mem0) | Working (primary in-process) + Factual (via integration) | Session transcript; offloads persistence to integrated memory service | Delegated | Delegated; the agent is intentionally memory-agnostic |

### Observations from the placement exercise

1. **Production coding agents (Claude, ChatGPT, OpenClaw) occupy the simplest corner of the cube.** They are nearly all token-level + flat + factual, with retrieval reduced to "inject everything" or "injected by tool call". This is a product choice (auditability, user control) not a capability ceiling.
2. **Mem0 and Graphiti, often compared head-to-head, live in different Form sub-cells.** Mem0 is Planar (facts + optional entity graph); Graphiti/Zep is Hierarchical (temporal knowledge graph with layered episodic/semantic edges). The survey's vocabulary makes that structural gap crisp.
3. **Hindsight is unusual in spanning all three Functions.** Its epistemic separation (world / experience / observation + deprecated opinion) plus Cara's reflect loop gives it the broadest Function coverage of any OSS system we track. This matches its benchmark advantage.
4. **MemOS is the only system that spans all three Forms.** Its explicit ParaMem (LoRA) + ActMem (KV/latent) + token-level stores mirror the survey's Forms axis almost 1:1, which is not coincidental — both are from the same Chinese memory-systems research community.
5. **Letta is the anomaly**: its *substrate* is token-level like everyone else, but its *management locus* is unique — the LLM edits its own memory from inside the context window. The survey doesn't give this its own axis, which is arguably a gap (see §8).
6. **No system in our collection uses parametric or latent memory as a primary store.** That gap is exactly where the survey points its open-problems section.

## 5. Benchmarks Discussed

The survey compiles benchmarks along use-case axes rather than by numerical comparison. The coverage reported in its benchmark table:

| Category | Benchmarks | What the survey says |
|---|---|---|
| **Long-context / multi-session dialogue** | **LoCoMo**, **LongMemEval** | Test persistence of facts across dozens of sessions and the ability to resolve temporal updates. LongMemEval in particular is called out as the de facto memory benchmark post-2024. |
| **Lifelong / streaming** | StreamBench | Tests drift detection and forgetting under non-iid streams. |
| **Agentic task benchmarks** | GAIA, SWE-bench Verified, BrowseComp, XBench | Not memory-native, but the survey argues these are where experiential memory shows the largest gains. |
| **Personalization** | Domain-specific (MemoryBank, ChatHaruhi-style) | Measures preference retention, persona stability. |
| **Multi-agent coordination** | Implicit in frameworks; no canonical benchmark yet | Identified as a gap. |

**What the survey flags as missing:**
- No unified evaluation protocol — each paper rolls its own splits and metrics.
- No isolation of memory contribution — gains are conflated with reasoning/planning improvements.
- No cost-aware benchmark — storage, retrieval latency, and token cost of memory operations are rarely measured.
- No trust/privacy benchmarks — poisoning, leakage, and consent are untested.
- Multi-agent and multimodal memory have essentially zero established benchmarks.

The survey's meta-point on benchmarking: **LongMemEval and LoCoMo are necessary but not sufficient** — they measure the token-level × factual cell only. There is no good benchmark for experiential memory, for working memory across long tasks, or for parametric/latent memory at all.

## 6. Open Problems / Frontiers

The survey's Section 7 identifies eight frontiers, ordered below roughly by how much they align with our repository's existing research directions (see `CLAUDE.md`).

1. **Memory automation** — moving from hand-designed consolidation / eviction policies to self-organizing memory. Hindsight's consolidation engine and trend computation is one of the few OSS examples; most systems still require operator tuning.
2. **RL integration** — formalizing `F`, `E`, `R` as learnable operators inside a POMDP rather than LLM-prompted heuristics. Tiny literature today; this is the *research* frontier most separated from *product*.
3. **Multimodal memory** — grounding across text, images, audio, embodied state. Survey cites M3-Agent, Ella, VideoAgent, Mem2Ego. Our repository has zero coverage here.
4. **Multi-agent shared memory** — concurrency, access patterns, consistency models. Every system we track is single-agent; G-Memory is the cited reference.
5. **Trustworthy memory** — privacy-preserving formation, poisoning defenses, explainability, consent management. ChatGPT's user-visible memory is a partial answer but not a technical one.
6. **Memory for world models** — persistent environment state supporting simulation and planning.
7. **Human-cognitive alignment** — closer mapping to biological consolidation (replay, sharp-wave ripples). Hindsight's biomimetic framing is the closest example in our set.
8. **Retrieval vs. generation** — a shift from "look it up" to "regenerate it from a compressed/latent prior". Memory³ and MemoRAG are early examples.

Relative to our repository's three research directions (Memory, Context, Learning — see `CLAUDE.md`), the survey's frontiers map as:
- **Memory** research direction ← frontiers 1, 2, 5, 7, 8.
- **Context** research direction ← only tangentially touched (the Working-memory function and retrieval post-processing).
- **Learning** research direction ← frontier 2 (RL-driven memory) + the parametric-memory sections partially answer "can models learn after deployment?". The survey's honest reading is: *parametric agent memory exists in the literature (ROME/MEMIT/LoRA), but no production coding agent uses it — all defer to external token-level memory*, which matches our own existing note in `CLAUDE.md`.

## 7. Takeaways

Eight bullets of "what this framework changes about how we think about our collection":

1. **Retire the long-term/short-term dichotomy.** Every existing `*.research.md` in the repo uses it; it is now superseded by the Functions axis (working / factual / experiential). Most "short-term" = working; most "long-term" = factual; experiential was typically missed entirely.
2. **"Graph memory" is not a level of analysis.** Mem0, Graphiti, Hindsight, and A-MEM all claim to be graph-based, but they sit in different Form sub-cells (Planar vs. Hierarchical) and use entirely different Evolution operators. Name the sub-cell, not the marketing term.
3. **Production systems are clustered in one corner of the cube.** Token-level + factual + retrieval-heavy. This is a capability gap, not a design choice — parametric and latent memory have not yet found product-market fit despite decade-plus research maturity.
4. **Hindsight and MemOS are the two "broad" systems in our set.** Hindsight is broad on Functions (world/experience/observation); MemOS is broad on Forms (token/parametric/latent). Together they define the current frontier of what production-grade agent memory can look like.
5. **Letta is outside the survey's main axis.** The survey classifies by *what* memory is and *how* it changes, but not by *who* manages it. Letta's defining feature — LLM-edits-its-own-memory — is orthogonal to the taxonomy. This is a genuine limitation of the framework (see §8).
6. **Evolution is where the taxonomy is sharpest.** Consolidation / updating / forgetting maps cleanly onto Mem0's CRUD, Graphiti's bi-temporal invalidation, Hindsight's observation synthesis, and Letta's in-context rewrites. It is the most immediately useful lens for vendor comparison.
7. **Benchmarks are drastically undercalibrated.** LongMemEval and LoCoMo both measure only the token-level × factual × retrieval cell. Hindsight's 91.4% LongMemEval score does not say anything about experiential or parametric memory. We need different benchmarks — or honest "this is a factual-memory benchmark" framing — to evaluate agent memory as the survey defines it.
8. **The taxonomy matches our CLAUDE.md research directions better than expected.** Memory ≈ Functions axis; Context ≈ Working-memory sub-function; Learning ≈ Parametric + Latent forms. Adopting the survey's vocabulary would make the repository's three-pillar structure legible to outsiders.

## 8. Limitations (of the Survey Itself)

A 47-author survey is unusual and worth criticizing on its own terms.

1. **Incentive for inclusiveness over judgment.** With 47 authors drawn from many labs, the survey is structured as a *map*, not an opinion piece. It does not rank systems, does not call out weak work, and does not name which frontier it thinks is most important. For practitioners wanting to pick a system, the survey is less useful than a smaller, opinionated review.
2. **Taxonomy orthogonality is aspirational.** In practice the three axes are heavily coupled. Parametric form almost always implies a generalization-oriented function; latent form almost always implies working-memory function; hierarchical token-level form almost always implies sophisticated evolution. The 3×3 cube has many empty cells, and the survey does not explicitly acknowledge that the cells are correlated.
3. **The "who manages the memory" question is missing.** Letta's in-context self-management, Hindsight's agentic reflect loop, and Mem0's externally-driven API are architecturally different, but the taxonomy lumps them together under token-level factual memory. An axis for *locus of control* (LLM-managed vs. service-managed vs. human-managed) would be a useful fourth dimension.
4. **The "how persistent" question is under-specified.** Session-scoped, user-scoped, and cross-user memory are operationally completely different (privacy, concurrency, cache invalidation). The survey groups them under Factual without distinguishing lifetime.
5. **Chinese research community over-representation.** The companion paper list and the main contact (guibinz@u.nus.edu, NUS) suggest heavy representation from East-Asian memory-systems labs. Many recent Western production systems (e.g., Hindsight's full epistemic-separation architecture, Letta's MemGPT lineage) get less detailed treatment than their academic counterparts (MemoryLLM, HippoRAG, MemOS).
6. **Benchmarks section is a catalog, not a critique.** It lists LongMemEval, LoCoMo, StreamBench, GAIA, but does not actually evaluate which of them is diagnostic for which cell of the cube. This is the most concrete missing piece relative to a practitioner's needs.
7. **The "agent memory ≠ RAG" distinction is argued but not proved.** The survey asserts that RAG is static and agent memory is self-evolving, but many production RAG systems now have automatic index refresh, feedback loops, and user-authored updates. The line is blurrier than the survey claims.
8. **No cost model.** The entire taxonomy ignores dollars, latency, and storage — yet most production choices today are cost-driven (Mem0 cheaper than Graphiti because no Neo4j; Claude Memory no-op because user edits are free). A framework that cannot explain vendor decisions is limited.

Despite these limitations, the survey is the best-organized view of the field to date and is worth adopting as the vocabulary for this repository's future work.
